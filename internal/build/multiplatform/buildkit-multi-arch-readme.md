# BuildKit Multi-Architecture Build Support for Pack

## Overview

This package adds multi-architecture container image building to `pack` using BuildKit.
Instead of running lifecycle phases as individual Docker containers (pack's default approach),
this feature generates a Dockerfile that runs all lifecycle phases inside BuildKit, enabling
cross-platform builds via QEMU emulation.

## How It Works

### Architecture

```
pack build --buildkit --platforms linux/amd64,linux/arm64 --publish ...
                        │
                        ▼
┌───────────────────────────────────────────────┐
│  Pack CLI (build.go)                           │
│                                               │
│  1. Fetch builder image metadata              │
│  2. Extract buildpack order from builder      │
│  3. Construct lifecycle phase commands        │
│  4. Select build backend (auto/dockerfile/llb)│
│  5. Dispatch to MultiPlatformExecutor         │
└───────────────────┬───────────────────────────┘
                    │
                    ▼
┌───────────────────────────────────────────────┐
│  MultiPlatformExecutor                         │
│                                               │
│  1. Check existing tag policy                 │
│  2. Dispatch to backend.BuildMultiPlatform()  │
│  3. Assemble manifest list from digests       │
└───────────────────┬───────────────────────────┘
                    │
                    ▼
┌───────────────────────────────────────────────┐
│  DockerfileBackend                             │
│                                               │
│  1. Generate Dockerfile                       │
│  2. Run: docker buildx build                  │
│     --platform linux/amd64,linux/arm64        │
│     --output type=cacheonly                    │
│  3. Parse lifecycle digests from output       │
│  4. Return per-arch digests                   │
└───────────────────┬───────────────────────────┘
                    │
                    ▼
┌───────────────────────────────────────────────┐
│  BuildKit daemon (docker-container driver)     │
│                                               │
│  Per platform (parallel):                     │
│    FROM <builder-image>                       │
│    RUN write /cnb/order.toml (custom order)   │
│    COPY app → /workspace                      │
│    RUN --mount=type=secret  analyzer          │
│    RUN                      detector          │
│    RUN --mount=type=cache   restorer          │
│    RUN                      builder           │
│    RUN --mount=type=cache+secret  exporter    │
└───────────────────────────────────────────────┘
```

### Generated Dockerfile Structure

```dockerfile
# syntax=docker/dockerfile:1
# Generated by pack for multi-platform build

FROM <builder-image>
USER root

# Inject custom buildpack order (from pack's order resolution)
RUN /bin/bash <<'ORDER_EOF'
cat > /cnb/order.toml << 'TOML'
[[order]]
  [[order.group]]
    id = "paketo-buildpacks/go"
    version = "4.19.24"
TOML
ORDER_EOF

ARG TARGETARCH

RUN mkdir -p /cache && chown -R 1001:1001 /cache
ENV CNB_PLATFORM_API=0.15
USER 1001:1001
COPY --chown=1001:1001 . /workspace
WORKDIR /workspace

# Analyzer: needs registry credentials (no buildpack code runs here)
RUN --mount=type=cache,id=<cache-id>-${TARGETARCH},target=/cache,uid=1001,gid=1001 \
    --mount=type=secret,id=docker-config,target=/home/cnb/.docker/config.json \
    /cnb/lifecycle/analyzer -run-image <run-image> <image-name>-${TARGETARCH}

# Detector: NO credentials (buildpack code runs here)
RUN /cnb/lifecycle/detector -app /workspace

# Restorer: NO credentials (reads from cache)
RUN --mount=type=cache,id=<cache-id>-${TARGETARCH},target=/cache,uid=1001,gid=1001 \
    /cnb/lifecycle/restorer -cache-dir /cache

# Builder: NO credentials (buildpack code runs here)
RUN /cnb/lifecycle/builder -app /workspace

# Exporter: needs registry credentials (no buildpack code runs here)
RUN --mount=type=cache,id=<cache-id>-${TARGETARCH},target=/cache,uid=1001,gid=1001 \
    --mount=type=secret,id=docker-config,target=/home/cnb/.docker/config.json \
    /cnb/lifecycle/exporter -app /workspace -cache-dir /cache <image-name>-${TARGETARCH}
```

### Key Design Decisions

1. **BuildKit as execution engine only**: BuildKit's output is discarded (`--output type=cacheonly`).
   The lifecycle exporter pushes the final app images directly to the registry with proper CNB
   metadata, labels, and entrypoint configuration.

2. **Single buildx invocation**: Both platforms build in parallel within a single
   `docker buildx build --platform linux/amd64,linux/arm64` call. BuildKit handles parallelism
   and QEMU emulation internally.

3. **Per-architecture cache scoping**: The `${TARGETARCH}` BuildKit ARG is used in the cache mount
   ID to ensure amd64 and arm64 lifecycle caches don't interfere with each other.

4. **Order injection**: The builder's buildpack order is extracted from image labels and written
   into the Dockerfile as `/cnb/order.toml`. This ensures consistent detection behavior across
   platforms regardless of what the builder image's default order contains.

5. **Phase isolation**: Each lifecycle phase is its own `RUN` instruction. Phases that run
   buildpack code (detector, builder) do NOT have `--mount=type=secret` — they cannot access
   registry credentials. Only the analyzer and exporter get the secret mount for Docker config.
   This provides the same security isolation as pack's untrusted builder flow without requiring
   `--trust-builder`.

6. **Manifest list assembly**: After the lifecycle exports per-arch images, pack assembles them
   into a manifest list using `docker buildx imagetools create` with digest references.

## Usage

### Basic Multi-Architecture Build

```bash
pack build registry.example.com/myapp:latest \
  --path ./app \
  --builder paketobuildpacks/ubuntu-noble-builder:latest \
  --platforms linux/amd64,linux/arm64 \
  --buildkit \
  --publish \
  --buildkit-builder pack-multiplatform
```

### With Custom Run Image and Cache

```bash
pack build registry.example.com/myapp:latest \
  --path ./app \
  --builder paketobuildpacks/ubuntu-noble-builder:latest \
  --run-image paketobuildpacks/ubuntu-noble-run-tiny:latest \
  --platforms linux/amd64,linux/arm64 \
  --buildkit \
  --publish \
  --buildkit-builder pack-multiplatform \
  --buildkit-cache-from type=registry,ref=registry.example.com/myapp-cache:latest \
  --buildkit-cache-to type=registry,ref=registry.example.com/myapp-cache:latest,mode=max
```

### Controlling Existing Tag Behavior

```bash
# Fail if the tag already exists
pack build registry.example.com/myapp:latest \
  --buildkit --platforms linux/amd64,linux/arm64 --publish \
  --existing-tag-policy fail

# Overwrite silently
pack build registry.example.com/myapp:latest \
  --buildkit --platforms linux/amd64,linux/arm64 --publish \
  --existing-tag-policy overwrite
```

## Prerequisites

- Docker with BuildKit support (Docker Engine 23.0+)
- A `docker-container` buildx builder for multi-platform builds:
  ```bash
  docker buildx create --name pack-multiplatform --driver docker-container --bootstrap
  ```
- QEMU user-mode emulation registered (default on Docker Desktop; on Linux: `docker run --privileged --rm tonistiigi/binfmt --install all`)
- Multi-architecture builder and run images
- `--publish` flag (multi-arch images cannot be loaded to a local daemon)

## Caching

### BuildKit Layer Cache

BuildKit caches the result of each `RUN` instruction independently. Since each lifecycle phase
is its own `RUN` command, BuildKit can cache phases individually. For example, if only your
app source changes, the `FROM` and `RUN mkdir` steps are cached, but `COPY . /workspace` and
all subsequent phases re-run (because the COPY invalidates downstream layers).

Configure external cache for CI environments (where the buildkit daemon is ephemeral):

```bash
--buildkit-cache-from type=registry,ref=myapp-cache:latest
--buildkit-cache-to type=registry,ref=myapp-cache:latest,mode=max
```

### Lifecycle Buildpack Layer Cache

The lifecycle's own caching (restorer/exporter) operates via `--mount=type=cache` which persists
across builds on the same BuildKit daemon. This is scoped per-architecture using `${TARGETARCH}`
in the cache mount ID. Even when source code changes (invalidating BuildKit's layer cache),
the lifecycle cache mount persists and allows buildpacks to reuse dependency layers
(e.g., downloaded Go modules, compiled dependencies).

Only the restorer, exporter, and analyzer phases receive the cache mount — the detector and
builder phases don't need it.

### Clearing All Caches

When `--clear-cache` is passed:
- `--no-cache` is added to `docker buildx build` (disables BuildKit layer cache)
- The `--mount=type=cache` is omitted from all lifecycle phases
- The `-cache-dir /cache` argument is removed from restorer/exporter commands

This forces a completely fresh build with no cached state from any source.

## Flags Reference

| Flag | Description |
|------|-------------|
| `--buildkit` | Enable BuildKit backend (experimental, required for `--platforms`) |
| `--platforms` | Comma-separated target platforms (e.g., `linux/amd64,linux/arm64`) |
| `--build-backend` | Backend selection: `buildkit-dockerfile` (default), `buildkit-llb` |
| `--buildkit-builder` | Name of the buildx builder to use |
| `--buildkit-cache-from` | External cache source for buildkit |
| `--buildkit-cache-to` | External cache destination for buildkit |
| `--existing-tag-policy` | Behavior when tag exists: `warn` (default), `fail`, `overwrite` |

## Troubleshooting

### Clearing the Cache

When `--clear-cache` is passed, pack disables both cache layers:
- **BuildKit layer cache**: `--no-cache` is added to the `docker buildx build` command,
  forcing all Dockerfile instructions to re-run from scratch.
- **Lifecycle buildpack cache**: The `--mount=type=cache` is omitted from the Dockerfile,
  so the lifecycle restorer/exporter have no persistent cache to read from or write to.

```bash
pack build registry.example.com/myapp:latest \
  --buildkit --platforms linux/amd64,linux/arm64 --publish \
  --buildkit-builder pack-multiplatform \
  --clear-cache
```

### Corrupted BuildKit State (I/O Errors)

If the build fails with errors like:
```
input/output error
failed to compute cache key: write .../snapshots/.../fs/...: input/output error
```

This typically means the buildkit daemon's storage is corrupted (often caused by running
out of disk space during a previous build). To fix:

```bash
# Remove and recreate the buildkit builder
docker buildx rm pack-multiplatform
docker buildx create --name pack-multiplatform --driver docker-container --bootstrap
```

### Clearing BuildKit Cache Without Recreating

If builds are using stale cached layers but the state isn't corrupted:

```bash
# Prune all build cache for the builder
docker buildx prune --builder pack-multiplatform --all -f
```

### Disk Space Issues

Multi-architecture builds require significant disk space (the builder image is pulled
once per platform). If you run out of space:

```bash
# Free up space from unused docker resources
docker system prune -f

# Prune buildkit builder cache
docker buildx prune --builder pack-multiplatform --all -f

# Check docker disk usage
docker system df
```

Consider increasing Docker Desktop's disk allocation in Settings > Resources.

### QEMU / Exec Format Errors

If you see `exec format error` for buildpack binaries on a non-native platform:
1. Ensure QEMU is registered: `docker run --privileged --rm tonistiigi/binfmt --install all`
2. If the error persists after QEMU is installed, the buildkit builder state may be corrupt
   (see "Corrupted BuildKit State" above)
3. Verify the builder image is truly multi-arch: `docker buildx imagetools inspect <builder-image>`

### Detection Failures on One Platform

If detection passes on one architecture but fails on another, the builder image's arm64/amd64
variants may have different buildpack configurations. Workarounds:
- Pass `--buildpack <buildpack-name>` to force a specific buildpack order
- Verify both platform variants contain the expected buildpacks:
  ```bash
  docker run --rm --platform linux/arm64 <builder-image> ls /cnb/buildpacks/
  docker run --rm --platform linux/amd64 <builder-image> ls /cnb/buildpacks/
  ```

## Limitations

- Requires `--publish` (multi-arch manifest lists cannot be loaded to a local Docker daemon)
- The `docker-container` buildx driver cannot access local-only images (`pack.local/...`);
  the Dockerfile references the original remote builder image and injects order/buildpacks separately
- Cross-platform builds use QEMU emulation which is slower than native compilation
- The `buildkit-llb` backend is a stub that falls back to `buildkit-dockerfile` (future work)

## Future Work

- **LLB Backend**: Direct BuildKit Go SDK integration for streaming progress, no Dockerfile
  intermediate, and finer-grained control
- **OCI Layout Export**: Export per-arch images to local OCI layout, assemble manifest list
  using `go-containerregistry` in-process, push atomically (no registry access during build)
- **Buildah Backend**: Support for `podman`/`buildah` multi-platform builds
- **Buildpack COPY layers**: For custom `--buildpack` flags, copy buildpack binaries from
  their OCI images via `COPY --from` stages rather than needing an ephemeral builder
