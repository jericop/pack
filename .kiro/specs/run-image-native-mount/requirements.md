# Requirements: Run-Image Native Mount (eliminate -pull-run-image network pull)

## Introduction

In the BuildKit LLB OCI-layout backend, the lifecycle analyzer currently receives
`-pull-run-image`, which performs a network pull of the run image into the layout
directory (`/output/<ParseRefToPath(runImage)>`) from INSIDE a BuildKit `RUN`
vertex. This has two drawbacks:

1. The network pull happens inside the build graph, is not content-addressed by
   BuildKit's vertex cache, and can re-run across builds (poor caching, extra
   time, and a network dependency inside the build).
2. It couples the feature to a lifecycle that must fetch the run image itself.

This spec replaces that with a NATIVE approach: BuildKit surfaces the run image's
digest-addressed blobs (config + manifest + compressed layers) read-only, pack
generates a minimal synthetic `index.json`, and the lifecycle reads the run image
from that mounted OCI layout WITHOUT a network pull. The run image's original
compressed layer blobs and diffIDs are preserved, so rebase and layer reuse keep
working.

This work depends on and extends the `oci-layout-tag-elimination` spec (the LLB
two-phase OCI-layout build). It is an OPTIMIZATION / architecture-cleanup; the
build is already correct without it.

## Glossary

- **Run image**: the base image the app image is built on; its layers form the
  rebase boundary.
- **OCI layout**: an on-disk directory of `index.json` + `oci-layout` +
  `blobs/sha256/<digest>` (content-addressed blobs).
- **`llb.OCILayoutBlob`**: a BuildKit LLB source that surfaces a SINGLE
  digest-addressed blob from an attached OCI store as one file.
- **OCI store (SolveOpt.OCIStores)**: a content store the client attaches to a
  solve; the LLB backend already attaches one for the Phase 2 import.
- **Synthetic index.json**: a minimal OCI image index (single manifest
  descriptor) generated by pack pointing at the run image's manifest digest.
- **diffID / layer digest**: the identifiers rebase depends on; must be preserved
  bit-for-bit (no re-tarring of an unpacked rootfs).

## Requirements

### Requirement 1: Eliminate the in-build network pull of the run image

**User Story:** As a pack maintainer, I want the run image provided to the
lifecycle without a network pull inside the BuildKit build, so that builds do not
depend on registry access mid-graph and the run image is acquired in a
content-addressed, cacheable way.

#### Acceptance Criteria

1. WHEN the LLB backend builds in OCI-layout mode THE backend SHALL NOT pass
   `-pull-run-image` to the analyzer.
2. WHEN the run image is required by the lifecycle THE run image SHALL be
   acquired once on the host (pulled into an OCI content store) and provided to
   the build via BuildKit-native sources, not via a network pull inside a RUN.
3. WHERE the same run image is used by multiple platform solves in one build THE
   run image content SHALL be deduplicated (pulled once, reused per platform).

### Requirement 2: Preserve run-image layer identity (rebase safety)

**User Story:** As a buildpacks user, I want rebase to keep working after this
change, so that swapping the run image later does not require rebuilding.

#### Acceptance Criteria

1. WHEN the exporter assembles the app image THE run image's ORIGINAL compressed
   layer blobs SHALL be reused by digest (no re-tarring of an unpacked rootfs).
2. THE run image's config digest, manifest digest, and layer diffIDs recorded in
   `io.buildpacks.lifecycle.metadata` (runImage.reference / topLayer) SHALL match
   the values that a normal registry-based build would record.
3. WHEN comparing a per-arch image built with this change against one built with
   `-pull-run-image` (same inputs) THE run-image base layer digests SHALL be
   identical.

### Requirement 3: Provide the run image as a mountable OCI layout

**User Story:** As a pack maintainer, I want the run image presented to the
lifecycle as a valid OCI layout directory it already knows how to read, so that
the lifecycle read path needs no changes.

#### Acceptance Criteria

1. THE run image SHALL be presented at the path
   `filepath.Join("/output", layout.ParseRefToPath(runImageRef))` (the path the
   lifecycle resolves from the run-image reference).
2. THE presented directory SHALL contain `blobs/sha256/<digest>` for the run
   image's config, manifest, and every layer, streamed as the ORIGINAL
   compressed blob bytes.
3. THE presented directory SHALL contain a minimal `index.json` (single manifest
   descriptor pointing at the run image's manifest digest) generated by pack; an
   `oci-layout` marker MAY also be written.
4. THE mount SHALL be read-only; nothing in the lifecycle writes into the
   run-image subpath.

### Requirement 4: Minimal, opt-in lifecycle change

**User Story:** As a lifecycle maintainer, I want the smallest possible change to
consume the mounted run image, so that the read path and default behavior are
unchanged.

#### Acceptance Criteria

1. THE lifecycle SHALL provide a way (a flag, or layout-mode behavior) to use the
   run image already present at the layout path WITHOUT attempting a network pull.
2. WHEN the run-image layout is already present at the expected path THE analyzer
   SHALL NOT attempt `PullToLayout` (it already self-skips when the path exists;
   this behavior SHALL be relied upon or made explicit via the new flag).
3. THE analyzer read path (`layout.FromBaseImagePath` → `FromPath` → lazy
   `blobs/sha256` reads) SHALL remain unchanged.

### Requirement 5: Correctness parity with the current implementation

**User Story:** As a maintainer, I want the produced images to be identical in
substance to the current working implementation, so that this is a pure
optimization.

#### Acceptance Criteria

1. WHEN a multi-arch app is built with this change THE published manifest list
   SHALL contain one entry per platform with correct os/arch, and NO intermediate
   per-arch tags (same guarantee as today).
2. WHEN each per-arch image is inspected THE image SHALL be a well-formed
   launchable CNB image (all CNB labels incl `io.buildpacks.lifecycle.metadata`,
   multiple real layers, launch process binary present) — verified via the MVP
   local build strategy.
3. THE change SHALL be validated with the local two-build (cold + rebuild)
   strategy against `samples/go/no-imports` publishing to the local registry.
