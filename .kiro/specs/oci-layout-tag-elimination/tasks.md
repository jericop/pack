## Task 3: Multi-platform manifest list assembly (native)
- [x] Determine the correct way to get BuildKit to assemble the manifest list from per-arch images that originate from separate per-arch OCI layouts
- [x] Options: single multi-platform solve vs combining per-arch results; prototype and pick
- [x] Verify the manifest list is pushed with an entry per platform and NO intermediate tags

- References: FR-5, design.md open item 1
- DECISION: Option (b) "combine per-arch results". The LLB backend uses the `client.Solve` API with a separate per-arch content store per platform; a single `llb.OCILayout()` source is one platform and there is no `client.Solve` way to drive a multi-platform `ExporterImage` from N separate stores (native single-solve would require the gateway frontend API). Per the design's documented fallback, per-arch layouts are assembled into one image index and pushed atomically via go-containerregistry (`remote.WriteIndex`) with NO intermediate tags.
- IMPLEMENTED in `oci_layout_push.go` (`AssembleManifestList` pure/testable + `pushIndex` network + `PushPerArchLayoutsAsManifestList` entry point) and `backend_llb.go` (`BuildMultiPlatform` runs per-arch Phase 1 only for multi-arch, then `assembleAndPushManifestList`; single-arch keeps native Phase 2 push under the final name).
- VERIFIED without a daemon via `oci_layout_push_test.go`: assembles the index from synthetic per-arch OCI layout fixtures and asserts exactly one entry per platform with correct os/arch/variant descriptors, content-addressed references (no tag names). Live push verification (entry-per-platform + no intermediate tags on a real registry) is DEFERRED to Task 10 (env-var gated).
